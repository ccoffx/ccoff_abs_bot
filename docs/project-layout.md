# 项目目录说明

根目录的 `main.go` 只负责调用 `app.Run()`。业务代码放在 `internal/` 下，以 Go 包隔离依赖；从项目根目录运行和构建即可，无需逐个指定 `.go` 文件。

## 功能入口

| 功能 | 代码位置 |
| --- | --- |
| 启动和数据库初始化 | `internal/app/runtime.go`、`internal/app/database.go` |
| Telegram 消息路由、管理菜单 | `internal/app/router.go`、`internal/app/*callbacks.go` |
| 定时调度、账号到期处理 | `internal/app/scheduler.go` |
| 开放注册、用户补偿和管理操作 | `internal/app/admin_*.go` |
| 注册、绑定和账号状态 | `internal/account/` |
| 邀请拉新、签到、财富榜 | `internal/account/` |
| 求书工单、入库事件和公告投递 | `internal/books/` |
| 斗气配置、突破和材料兑换 | `internal/game/cultivation*.go` |
| 药园和背包 | `internal/game/garden.go` |
| 宗门、科技、喇叭、宗门抽奖和秘境 | `internal/game/sect*.go` |
| 听书统计、跨日修正、违规检测和排行榜 | `internal/game/*listening*.go`、`internal/game/abs_cross_day_*.go`、`internal/game/leaderboard.go` |
| 世界 Boss | `internal/game/world_boss.go` |
| 境界、称号、榜首荣誉和群标签 | `internal/realm/`、`internal/titles/` |
| 抽奖、红包、盲盒和寻宝 | `internal/activity/` |
| 交易行和卡密回收 | `internal/market/` |

斗气、宗门和听书修为共用结算规则，暂时保留在同一个 `game` 包中，避免这些玩法互相导入而产生循环依赖。

## 公共能力

| 包 | 职责 |
| --- | --- |
| `model` | 按账号、钱包、宗门、活动等分类的 GORM 模型与表名定义 |
| `storage` | 数据库连接状态、索引、系统配置、账号资格、钱包事务、卡密、审计和安全校验 |
| `rankings` | 财富、斗气、宗门榜与榜首称号共用的资格、排序和并列规则 |
| `lifecycle` | 跨业务的 ABS 账号恢复、播放冻结解除与持久化生命周期互斥保护 |
| `telegram` | 消息发送队列、自动删除、回调应答、菜单、群成员校验、会话和用户锁 |
| `abs` | Audiobookshelf 请求、账号管理和统计 API；听书报告的修为计算在 `game` 中 |
| `config` | `.env` 与环境变量加载、必填配置校验 |
| `security` | 安全令牌哈希、校验和密码学随机数 |
| `backup` | 数据库快照、备份加解密和文件分片 |
| `metrics` | 消息队列、API 请求和慢处理的运行指标 |
| `textfmt` | Markdown 转义、敏感信息脱敏、文本与数字解析 |

`app` 负责组装业务模块。公共包不导入业务包；需要新增跨业务能力时，优先放入职责对应的公共包，保持依赖单向。模型集中声明，首次部署按当前模型和索引定义创建完整数据库。业务代码统一使用当前结构；异火相关表缺失、活动配置或公告预览快照不完整时返回错误，不提供开发期旧结构和旧数据的补迁入口。

### 累计数值与听书同步

药草收获数、成丹数存放在 `garden_production_totals`，宗门商店累计贡献消费存放在 `sect_shop_contribution_totals`。`storage/business_totals.go` 在首次升级时按现有明细回填一次，后续通过 SQLite 触发器在原业务事务内维护差额，覆盖数量修正、软删除、恢复、硬删除与换绑。称号榜和累计贡献资格查询直接读取累计值；明细继续保留用于审计。重复启动不会重扫历史；累计表缺失时会从明细重建。

听书修为按每日新旧已结算金额的差额更新。普通同步读取 ABS `listening-stats.days`，只更新未归档日期；今天最多计入北京时间零点至当前经过的秒数。首次接入/离线缺失日期导入一次，已有闭日历史在首次升级时保留余额并归档。尚未关闭的日期，须由该日结束后发起的请求实际返回该日期统计，才补取一次闭日值并归档；缺少日期时保留原记录和待关闭状态，后续同步及重启继续等待，显式零值则正常关闭。归档后不接受 ABS 历史变化，修正需走显式修复。`ListeningReportSnapshot.OfficialInputJSON` 缓存修为输入，缓存失效时从数据库恢复，不重新计算归档日。报告不展示或保存 ABS 账号累计上报时长，普通修为与活动均不读取 `totalTime`。输入、修为差额和报告快照同事务提交。

Boss、秘境的状态、排行和明细均只读数据库。后台约每 2 分钟以最多 3 名参与者并发读取统计快照，每人一次 `listening-stats`，不读取 `listening-sessions`。入场保存当日有效听书基线，后续按入场日起至截止日的每日有效秒数减基线（支持跨午夜），再按实际参与时间封顶。有效秒数与普通每日听书共用时间上限计算；活动单独保存窗口内各日高水位和归档状态，缺少日期继续等待，归档后忽略历史增长，不受更早历史日期修正影响。已有进行中的记录若缺少日基线，首次成功刷新时保留已发布进度并重建当日日基线，后续只累计新增进度，不再使用旧累计基线。实时进度快照独立持久化，不发放奖励；榜单汇总与展示数据在同一事务发布。发布事务重新核对账号状态、原绑定和秘境成员资格，失效参与者即使本轮采样失败也清除旧战况，并排除其伤害及护法加成。

活动每 15 秒巡检，实时统计仍以距上次完成约 2 分钟为刷新间隔。活动结束后进入最终同步；截止后 2 分钟内，额度排队超时、接口失败或响应缺少已知且未归档的非零听书日期时，会持久化待重试状态，每次失败后至少间隔 15 秒再试，不提前冻结或发奖。窗口耗尽（包括重启后补结算）才冻结最后保存的进度，没有成功刷新时为零。最终尝试次数、最近尝试时间、下次重试时间、错误分类和降级原因保存在参与者的 `ActivityListeningSnapshot` 中。`ActivityListeningSnapshot.Finalized` 在发奖前持久化，结算事务重试复用同一最终输入，不再次拉取活动结束后的累计值。Boss 提前击杀在发布击杀状态的同一事务保存独立截止时间，重启后复用；旧版缺少截止时间的击杀记录使用最后一次实时发布时刻恢复；每次读取统计并非同一秒，最终快照允许上述调度误差。后台快照写入要求活动仍处于对应状态且尚未冻结，避免覆盖最终输入。绑定、成员资格和防重复发奖检查保持在奖励事务中。秘境护法在发奖前失去资格时，整批奖励回滚并复用已冻结快照重新计算护法和加成；没有有效护法时清除旧护法信息。

听书同步使用统一的有界优先级额度调度（总并发 4、最多 512 个等待者），最终同步优先于报名入场，报名入场优先于活动实时刷新，再优先于普通同步；同优先级活动轮转，单场最多占用 3 个额度。已发出的请求不抢占。多个秘境按场独立处理，事件执行以活动键去重并限制最多 128 场在途，未被接纳的事件仍由数据库巡检发现；同一秘境的实时刷新和结算不会同时执行。明细展示听书采样时间、最终同步尝试次数和降级提示；日志记录每次额度等待、请求耗时及整轮耗时和失败人数。

Boss 和秘境入场共用 `ActivityEntryRequest` 持久化队列，按活动类型、活动编号、用户唯一登记；已有参与记录直接读库回复，不重新请求或覆盖基线。前台只做本地检查和登记，首次申请仅发送最终成功或失败结果，重复进入明确提示已经加入；结果由独立有界消息队列发送。入场准备使用 4 个后台 worker、最多 128 个在途任务，同一活动最多 3 个在途任务，多活动轮流投递，并共用听书请求优先级额度。待入场申请全服最多 512 条、单场最多 128 条，满时明确拒绝登记。

首次入场必须成功读取本人的当前 ABS 统计，不能因缓存兜底提前确认；等待请求额度或全服刷新屏障时保留申请，5 秒巡检恢复，最多 3 次实际采样尝试，申请有效期为两分钟且不超过活动报名截止。采样前后及提交事务内复核账号可用性、绑定、秘境原成员记录、境界和活动状态；请求发起、响应基线与正式入场日期须一致，跨日时重新采样。正式入场时间取提交时刻，不倒填申请时间；待入场不增加人数或 Boss 血量。参与记录、活动参与人数、Boss 血量和申请成功状态同事务提交；秘境后台刷新在发布事务中重新统计人数，避免旧采样名单覆盖刷新期间的新入场人数。重启恢复待处理申请和未送达结果；结果通知失败后持久化退避重试，间隔从 30 秒递增至最多 30 分钟，不因尝试次数耗尽而丢弃；群聊引用的原指令已被删除时允许独立发送结果，成功及失败结果均携带玩家姓名；失败后重新报名使用新一代申请，旧回调不能覆盖新状态。个人明细可读取排队或失败状态。

普通修为、报告和活动计算不再注册全账户历史扫描。历史修复队列仅处理显式提交的异常修复，保留独立的证据工具；历史修复不属于周期报告计算。

个人闭关与宗门闭关确认进入独立的有界准备队列（2 个 worker、64 个任务），分别按用户和宗门去重。基线准备采用本人空闲同步/本地回退，不等待全服刷新锁、同账号在途同步或请求额度；宗门成员基线最多 3 人并发准备。事务提交前复核操作人原成员记录、宗门权限、成员资格和绑定，原子扣费与创建闭关；起止时间从正式提交开始，不倒填排队时间。队列任务尚未创建闭关前不扣费，重启后可按洞府实际状态重新提交。

### 指令调度与后台任务

消息按用户保留到达顺序，但只有用户队首可执行的消息进入 worker 队列。后续消息不占 worker 等待前序操作，待处理消息总量仍受队列容量限制。`/start` 的网络发送由 worker 执行，接收循环不发送用户消息。

`internal/background` 为刷新、扫描、批量投递提供有容量限制、按任务键去重的后台队列（2 个 worker、64 个任务）；面板使用独立队列（4 个 worker、128 个任务），同一面板合并为最新状态。寻宝和护道通过 `PanelDirty`、`PanelVersion` 保留待发送状态，网络失败或重启后由巡检重试；`PanelNextRetryAt` 持久化 30 秒重试间隔，按重试时间轮转，避免前批失败记录阻塞后续面板。消息已删除或不可编辑时停止重试，新版更新可立即重试，旧请求不能清除或推迟新版更新标记。

斗气榜、个人信息、签到、听书报告和宗门任务读取已保存统计，不等待全服刷新。手动刷新本人、宗门、全服统计以及秘境结算、抽奖投递和求书公告候选扫描在后台执行。奖励、突破等严格操作在同步锁、同账号请求或 ABS 额度繁忙时立即拒绝等待；空闲时只同步本人，保留有效性校验。

管理员账号暂停/恢复先写入 `AccountLifecycleClaim`，网络请求期间释放 SQLite 写事务，再同事务删除 claim 并提交本地状态和审计。该 claim 与现有生命周期触发器、外部操作锁共用，防止换绑和自动恢复交叉；失败和重启后由后台重试。管理员状态操作持久化最近尝试时间、下次重试时间及次数，按未尝试优先、最早尝试顺序每批取 20 条；失败退避从 1 分钟递增至最多 30 分钟，避免持续失败的账号阻挡后续任务。

## 配置、部署与测试

- `.env.example` 是配置模板；实际 `.env` 与运行数据 `data/` 保留在根目录，并由 Git 忽略。
- `Dockerfile` 构建多架构镜像；`docker-compose.yml` 用于固定 digest 的正式部署，`compose.test.yml` 用于 Mac 测试 Bot；入口脚本在 `scripts/docker-entrypoint.sh`。
- `go run .`、`go test ./...`、`go vet ./...` 和 `go build -o ccoff-abs-bot .` 都从根目录执行。
- 包内测试随代码保留；`internal/app/` 的集成测试覆盖数据库新建与重启、备份、资产事务、并发领取和 Telegram 回调。
- 用户操作说明见 [用户使用指南](user-guide.md)。
- 自动回归、内置 ABS 模拟器和测试 Bot 操作见 [README](../README.md#验证)，镜像发布与运维见 [部署指南](deployment.md)。`internal/operations/` 提供不启动 Bot 的健康检查、SQLite 加密备份和恢复；`internal/buildinfo/` 保存构建与数据库兼容标识。


`internal/joinverify/`：关注频道入群验证，包含 Telegram 管理接口、持久化验证状态机、成员事件队列、验证按钮和超时恢复；通过 `internal/app` 接入消息与按钮业务门禁。对应持久化模型位于 `internal/model/join_verification.go`。


`internal/announcements/`：频道公告持久化投递、消息链接、群提醒、发送中断恢复和人工处置。`internal/app/channel_announcements.go` 接入注册/补偿状态及服务公告向导；`internal/activity/lottery_entry.go` 提供抽奖私聊深链接和二次确认。

Boss 和秘境实时刷新允许部分成功：成功参与者发布新进度，失败参与者保留上次已发布数据，并计入整场汇总；明确不符合资格的参与者清除预览。整场标记部分同步失败，但不阻止 Boss 血量更新和击杀判断。
