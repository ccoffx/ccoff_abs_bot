# 每日听书统计与跨天排查

## 刷新与日期口径

- `刷新我的今日净修为`、`刷新宗门今日净修为`、`刷新全服今日净修为` 均绕过 5 分钟缓存，实际请求 ABS 的 `listening-stats` 和 `listening-sessions`。普通查询仍可复用缓存。
- 统计日以北京时间零点切换。零点之后“今日”指新的一天，上一天的结果应通过 `查看每日净修为 TG_ID YYYY-MM-DD` 查询。
- ABS 的 `days` 可能把整段会话归到开始日。Bot 依据会话的实际 `timeListening`、`startedAt`、`updatedAt` 重新分日，不根据 `isPlaying`、播放进度或当前时间虚增听书秒数。
- 跨天分日沿用现有规则：停顿较少的会话按跨日区间比例估算；长时间停顿的会话只移动有数学下界保证的部分。没有逐段播放明细时，不能保证还原每一分钟的真实归属。
- ABS 尚未补报时，刷新只能显示 ABS 已提供的值。后续补报被拉到后，会重新校正涉及的历史日期和累计修为。不能用后来收到的 6.42 小时断言零点时 ABS 已经提供同样数据。

## 防止统计回落

会话接口失败、数据库校正失败，或已知跨天会话秒数大于同一来源日的 ABS 统计秒数时，整次每日统计写入失败，保留上一次成功的数据及 `LastFetchedAt`。不会再把未拆日的原始 `days` 当作成功结果覆盖校正值。可以再次手动刷新；定时任务也会按原有周期重试。

校验包含本次 `days` 缺失的来源日，不能因为来源日未返回就忽略已知跨天会话。播放异常巡检仍可使用当前会话的数学下界判断缺失日期的播放凭据；这种 `evidence_only` 结果不写入每日统计，也不更新缓存时间。明确返回的日统计与会话矛盾时，巡检仍等待重试。

ABS 删除历史会话后，只有完整会话列表已确认其缺失，且来源日全部剩余会话的秒数与 ABS 日统计一致，才将旧校正标记为 `invalidated`。会话被较新的 ABS 记录更正为同日时，也会撤销原有跨天分配。失效记录保留原分配日期，以便后续刷新清零已无听书的历史日期；晚到的旧响应不能恢复已失效的分配。

普通请求仍最多读取 5 页。历史超过 500 条、无法当场确认删除时，保留旧数据，并用现有后台扫描器核实完整历史；每批最多 5 页，失败续扫，重复手动刷新不会重置正在进行的核实。扫描证据和游标在同一事务提交，核实完成后下一次刷新恢复写入。现有 `abs_cross_day_session_scan_cursors` 表新增 `reconcile_started_at`、`reconcile_evidence_json` 两列，由启动时的 `AutoMigrate` 添加；不新增表。

听书报告刷新失败时，优先显示当前绑定账号的上次成功统计，并注明缓存更新时间；没有可用缓存时显示“读取失败”，不将未经校正的零值当作今日结果。

每日快照以统计请求开始时间排序，旧请求晚到不会覆盖新快照；会话观察以 ABS `updatedAt` 排序，同时间戳再比较本地观察时间。时间比较按实际时刻进行，不依赖 SQLite 时间字符串的字典序。较新的 ABS 正常修正仍允许降低秒数，不使用历史最大值锁死统计。

请求跨过零点时，按写入时的日期保留新一天的数据，但仍用请求开始时间判断快照新旧。

## 诊断日志

每次刷新输出带 `ABS listening trace:` 前缀的 JSON，不新增数据库表。日志包含 Telegram ID 和 ABS 用户 ID，请限制运维日志访问权限。

同一次常规刷新通过 `user_id`、`abs_user_id`、`fetched_at` 关联：

- `event=refresh`：是否强制刷新、统计接口 HTTP 状态、统计请求耗时、总耗时、最终结果和错误。`outcome=cache_hit` 表示未请求 ABS；`evidence_only` 表示巡检仅使用会话凭据、未写入每日统计；`updated` 才代表成功写入。
- `event=observation`：今日、昨日及校正日期的 ABS 原始秒数、分日校正秒数、普通有效小时数；会话数量、最新会话的秒数和 `updated_at`、距离本次拉取的间隔；最近 20 个跨天会话的分类及原因。`sessions_duration_ms` 包含会话读取、持久化和校正处理。`correction_ready=false` 时的校正值不是已写入结果。
- `event=write`：成功事务提交后记录各日的写入前后原始秒数、普通有效小时数、先前拉取时间和来源。旧快照被拒绝时标记 `ignored_older_snapshot`。首次导入不展开全部历史，仅记录最近日期；已存在历史日期的变动仍记录。

日志不主动记录令牌、请求头、整份响应或书名。个人净修为还可能包含闭关、异火加成；诊断里的 `effective_hours` 是普通听书折算值，不包含这些加成。

只读查询示例：

```sh
docker logs --since 24h ccoff_abs_bot 2>&1 | rg 'ABS listening trace:' | rg '"user_id":6526626684'
```

排查时按顺序核对：是否 `force=true`、是否真实发出请求、ABS 原始秒数和会话 `updated_at` 是否变化、校正是否通过、事务是否写入、页面或榜单读取的是哪个时间点。ABS 返回值未变只能说明 Bot 本次未从 ABS 读到新数据，不能单独证明客户端未上传；还需要客户端/ABS 的接收日志。

当前容器日志轮转为 10 MB、3 份，重建容器也可能丢失旧日志。需要长时间取证时，应把日志接入独立收集系统；本次未修改日志保留策略。

## 榜单边界

08:00 已发布的 Telegram 榜单目前是发送时的快照，后续每日数据校正不会自动修改旧消息。这与数据库分日校正是两条独立链路；不能把“数据库已更新”等同于“历史群消息已更新”。
